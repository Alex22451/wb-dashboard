# ИП Зубахина: автономный FBS-бот

Дата: 2026-08-12
Статус: утверждено пользователем
Проекты: новый `wb-fbs-bot-zubakhina` и ограниченная интеграция с `wb-dashboard`

## 1. Цель

Автоматизировать операционный процесс Wildberries FBS для ИП Зубахина:

1. Каждые 15 минут получать новые сборочные задания.
2. Определять тип товара по действующему маппингу WB Dashboard.
3. Определять ткань из артикула поставщика.
4. Объединять совместимые задания в одну открытую поставку.
5. В фиксированные окна передавать готовые поставки в доставку без ручного подтверждения.
6. Оставить сотрудникам только печать стикеров в кабинете WB.
7. Показывать состояние и ошибки бота в админской части WB Dashboard.

Бот является отдельным проектом. Бизнес-логика автоматизации не размещается внутри WB Dashboard.

## 2. Утвержденные правила

### Расписание

- Синхронизация новых заданий: каждые 15 минут.
- Часовой пояс: `Europe/Moscow`.
- Окна передачи в доставку: `05:00`, `10:00`, `15:00`, `20:00`.
- Девятичасовой ночной интервал после `20:00` является намеренным.
- В окно доставки бот сначала получает последние заказы, затем закрывает готовые автоматические поставки.
- Задание, пришедшее непосредственно перед окном, может попасть в поставку и быть передано в доставку в том же цикле.

### Ткани

Разрешенный список, регистр и разделители не учитываются:

- оксфорд;
- дюспо;
- джерси;
- сетка;
- габардин;
- велюр.

Если у разрешенного товара ткань не распознана однозначно, задание остается в `Новые`. Бот не изменяет его и публикует ошибку.

### Категории

- Тип товара вычисляется без размера.
- Источник истины — текущий маппинг `src/lib/wb-mapping.ts` в WB Dashboard.
- Разрешены только категории, которые участвуют в аналитике Dashboard.
- `EXCLUDED_WB_SUBJECTS` является черным списком. Такие задания бот молча не изменяет.
- Неизвестная или неоднозначная категория остается в `Новые` и отображается как ошибка.
- В частности, нельзя обрабатывать картины, картины по номерам и алмазные мозаики.

### Группировка

Ключ совместимости поставки строится по стабильным идентификаторам WB:

1. ИП/продавец.
2. Нормализованный тип товара без размера.
3. Нормализованная ткань.
4. `warehouseId` и идентификатор офиса/направления назначения.
5. Тип груза.
6. Cross-border признак.
7. Иные обязательные признаки совместимости, если их вернет WB API.

Город используется в названии и интерфейсе, но не является единственным техническим ключом. Размер, дизайн, цена, `nmId` и номер задания не разделяют совместимые товары.

### Название поставки

Формат:

```text
[AUTO] <Тип товара> <ТКАНЬ> <Город> <ДД.ММ> <ЧЧ:ММ>
```

Пример:

```text
[AUTO] Гобелены ДЮСПО Курск 12.08 15:00
```

До наступления окна все новые совместимые задания добавляются в одну открытую поставку. После передачи в доставку для следующих заданий создается новая поставка.

## 3. Архитектура

### Новый проект бота

- Отдельный репозиторий и Vercel-проект `wb-fbs-bot-zubakhina`.
- TypeScript и Next.js App Router, чтобы использовать стандартный Vercel runtime и API routes.
- У проекта нет пользовательского интерфейса и публичных команд управления.
- Единственная публично доступная рабочая точка входа принимает только запросы с валидной подписью QStash.

### Планировщик

Vercel Hobby не поддерживает Cron чаще одного раза в сутки, поэтому расписание выполняет Upstash QStash:

```text
CRON_TZ=Europe/Moscow */15 * * * *
```

QStash вызывает один цикл. Отдельные конкурирующие cron-задачи для загрузки и доставки не создаются. Внутри цикла бот определяет, наступило ли окно доставки.

### Хранилище

Отдельный Upstash Redis хранит только состояние FBS-бота:

- распределенную блокировку продавца;
- обнаруженные задания и результат классификации;
- открытые поставки и их групповые ключи;
- журнал мутаций;
- обработанные окна доставки;
- ошибки, heartbeat и агрегированную телеметрию.

Боту не выдаются учетные данные основной базы WB Dashboard. Ключи Redis имеют префикс версии, например `fbs:v1:`.

### Интеграция с Dashboard

WB Dashboard получает две изолированные серверные точки входа:

1. Пакетная классификация товара через существующий `wb-mapping.ts`.
2. Прием очищенного снимка состояния бота.

Обе точки защищены отдельным общим секретом. WB-токен не передается в Dashboard через эти запросы.

Бот получает карточки товаров из официального Content API, передает в классификатор только `subject`, `supplierArticle`, `brand` и технический идентификатор. Результат кешируется по `nmId` и версии маппинга. Если токен не имеет права Content, автоматизация не включается, пока источник категории не будет доступен.

При временной недоступности Dashboard бот может использовать последний подтвержденный кеш классификации. Новые неизвестные `nmId` не обрабатываются до восстановления связи.

## 4. Машина состояний

### Задание

```text
discovered
  -> ignored_blacklist
  -> blocked_unknown_category
  -> blocked_unknown_fabric
  -> eligible
  -> assign_planned
  -> assign_sent
  -> assigned_verified
  -> delivered_verified
```

Неоднозначный результат переходит в `reconcile_required`. Это состояние не разрешает новые мутации над заданием до подтверждения фактического состояния через WB API.

### Поставка

```text
create_planned
  -> create_sent
  -> open_verified
  -> delivery_due
  -> deliver_sent
  -> delivered_verified
```

Ошибочные ветки:

```text
reconcile_required
blocked
```

`blocked` снимается только после нового успешного чтения WB и прохождения всех инвариантов. Уже переданная поставка никогда не переоткрывается и не редактируется.

### Журнал операции

Каждая мутация имеет детерминированный `operationId`, тип операции, хеш входных данных, время, попытку, HTTP-результат и итог проверки. Состояния:

```text
planned -> sent -> verified
                 -> reconcile_required
```

WB API не предоставляет универсальный idempotency key. Поэтому бот не заявляет математическую гарантию exactly-once. Практический однократный эффект обеспечивают блокировка, детерминированные ключи, журнал и обязательная сверка с WB после каждого изменения.

## 5. Алгоритм цикла

1. Проверить подпись QStash.
2. Получить распределенную блокировку для ИП Зубахина с ограниченным TTL.
3. Сверить незавершенные и неоднозначные операции с WB.
4. Получить новые FBS-задания.
5. Загрузить недостающие данные карточек.
6. Применить черный список, маппинг и определение ткани.
7. Проверить обязательные метаданные и совместимость WB.
8. Найти либо создать открытую поставку для группового ключа.
9. Добавить задания пакетами не более 100 штук.
10. Перечитать состав поставок и статусы заданий.
11. Если наступило необработанное окно, выполнить преддоставочную проверку.
12. Передать прошедшие проверку поставки в доставку.
13. Перечитать поставки и подтвердить `done`/конечные статусы.
14. Записать heartbeat и отправить очищенный снимок в Dashboard.
15. Освободить блокировку.

## 6. Преддоставочные инварианты

Поставка может быть передана в доставку, только если одновременно выполнено все:

- поставка создана ботом и имеет ожидаемый групповой ключ;
- поставка открыта и еще не передана;
- фактический состав WB совпадает с подтвержденным журналом;
- все задания принадлежат ИП Зубахина;
- все задания имеют одинаковые обязательные признаки совместимости;
- нет неизвестной категории, ткани или обязательного metadata;
- нет операции в состоянии `sent` или `reconcile_required`;
- текущее окно еще не отмечено как обработанное;
- глобальный kill switch разрешает мутации;
- режим приложения не `shadow`.

Если WB требует упаковочные короба или другие действия, которые бот еще не умеет корректно выполнить, поставка остается `На сборке`, а Dashboard показывает блокирующую ошибку. Бот не подбирает данные коробов предположением.

## 7. Ошибки и ретраи

- `429` и документированные ограничения скорости: ждать интервал из заголовка WB с небольшим jitter.
- Без заголовка использовать консервативную паузу и не превышать официальный лимит.
- `409`: считать бизнес-конфликтом, не повторять автоматически; сначала перечитать заказ и поставку.
- `4xx`, кроме rate limit: зафиксировать ошибку данных/прав и не повторять без изменения состояния.
- `5xx` на чтении: ограниченный retry с backoff.
- Таймаут после мутации: не отправлять мутацию повторно вслепую. Перевести операцию в `reconcile_required`, перечитать WB в текущем и следующем цикле.
- После подтверждения, что эффект отсутствует и объект все еще допускает действие, разрешена одна контролируемая повторная попытка с тем же `operationId`.
- Необратимая доставка при неоднозначном ответе возвращает QStash успешный технический ответ и продолжает сверку по журналу. Это предотвращает неконтролируемый немедленный retry всего HTTP-запроса.

Все сообщения в логах проходят санитизацию. Запрещено логировать токены, заголовки авторизации, полные ответы с персональными данными и содержимое секретов.

## 8. Админская вкладка `FBS-бот`

Вкладка доступна только администратору и не содержит кнопок мутации.

Показывает:

- текущее состояние: работает, загрузка данных, задержка, ошибка, остановлен;
- время последнего успешного цикла;
- время следующего окна доставки;
- количество новых, распределенных, пропущенных и заблокированных заданий;
- открытые поставки и их подтвержденный состав;
- поставки, переданные в доставку;
- ошибки с безопасной причиной и идентификаторами WB;
- версию маппинга и возраст кеша классификации.

Если heartbeat старше 30 минут, Dashboard сам помечает состояние как просроченное, даже если бот не смог отправить отдельную ошибку.

## 9. Секреты и доступ

Секреты создаются только в окружении Vercel/Upstash и никогда не коммитятся:

- `WB_ZUBAKHINA_TOKEN`;
- `QSTASH_TOKEN`;
- `QSTASH_CURRENT_SIGNING_KEY`;
- `QSTASH_NEXT_SIGNING_KEY`;
- `FBS_BOT_REDIS_URL`;
- `FBS_BOT_REDIS_TOKEN`;
- `FBS_DASHBOARD_SHARED_SECRET`;
- `FBS_MUTATIONS_ENABLED`.

Перед production выполняется безопасная проверка прав нового базового токена на чтение Marketplace и Content. Право на Marketplace write проверяется по официальной категории токена и контрактам API без тестовой необратимой доставки.

## 10. Тестирование

По правилам проекта тестируется логика, а не дизайн.

Обязательные тесты:

- нормализация шести тканей и отрицательные примеры;
- черный список и неизвестные категории;
- групповой ключ, включая несовместимые склады и типы груза;
- вычисление четырех московских окон, включая переход даты и ночной интервал;
- повторный запуск одного и того же цикла;
- параллельный запуск и потеря блокировки;
- создание/добавление/доставка с успешной сверкой;
- таймаут после каждой мутации;
- `409`, `429`, `5xx` и частичный ответ;
- отсутствие обязательного metadata;
- устаревший кеш маппинга;
- сериализация безопасного статуса для Dashboard;
- replay обезличенных WB fixtures по сценарию из видео.

## 11. Ввод в эксплуатацию

1. Создать проект, Redis и QStash без включения мутаций.
2. Проверить права токена read-only запросами.
3. Запустить `shadow`-цикл и подтвердить классификацию реальных новых заданий.
4. Проверить, что картины и другие исключения не попадают в план.
5. Включить операции добавления `На сборку`, затем перечитать WB и подтвердить состав.
6. Разрешить автоматическую передачу в доставку только после прохождения всех проверок и уже полученного явного согласия пользователя на необратимый вызов.
7. Выполнить production smoke по состоянию WB и Dashboard.

Откат означает отключение QStash schedule либо `FBS_MUTATIONS_ENABLED=false`. Уже переданные в доставку поставки откату не подлежат.

## 12. Критерии готовности

- Бот работает как отдельный Vercel-проект.
- За 30 минут не возникает повторных поставок или двойного распределения одного задания.
- Совместимые задания до окна собираются в одну поставку.
- Несовместимые задания никогда не смешиваются.
- Исключенные и неизвестные товары не изменяются.
- Каждая мутация подтверждается повторным чтением WB.
- Передача в доставку выполняется только в утвержденные окна и только после preflight.
- Dashboard показывает достоверное админское состояние без WB-токена и ручных команд.
- Все логические тесты проходят, секреты отсутствуют в git и логах.

## 13. Официальные ограничения

- Vercel Hobby Cron допускает запуск только один раз в сутки, поэтому для 15-минутного расписания используется QStash: https://vercel.com/docs/cron-jobs/usage-and-pricing
- QStash поддерживает cron-расписание, timezone и подпись сообщений: https://upstash.com/docs/qstash/features/schedules
- Бесплатный QStash допускает 1000 сообщений в сутки, текущая схема требует около 96 плюс ограниченные ретраи: https://upstash.com/pricing/qstash
- Официальный FBS API WB: https://dev.wildberries.ru/openapi/orders-fbs/
